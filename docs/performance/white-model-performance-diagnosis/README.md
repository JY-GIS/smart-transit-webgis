# 城市白模 FPS 性能诊断报告

## 1. 诊断结论

城市白模开启后从约 148 FPS 降至约 72 FPS，主要原因是 Cesium 默认的 4 倍多重采样抗锯齿（4x MSAA）与密集建筑边缘叠加，显著增加了 GPU 像素采样和填充压力。

本轮测试未发现福田区多边形裁剪产生可测的额外 FPS 损失；将 `maximumScreenSpaceError` 从 16 调至 32 也没有产生可测改善。因此，这次性能下降不属于白模裁剪代码 Bug，也不以瓦片 LOD 为主要瓶颈。

最终方案是在原生渲染分辨率下将 `msaaSamples` 设为 1，关闭 MSAA，同时保留：

- 福田区多边形裁剪；
- `maximumScreenSpaceError: 16` 的原始模型精度；
- 原生渲染分辨率。

应用该方案后，开启白模的稳定帧率恢复到 150 FPS 以上，画面清晰度正常。

## 2. 测试方法

测试时固定相机视角、窗口大小和车辆显示模式，等待当前视角瓦片基本加载完成后读取 Cesium FPS。每组只改变一个主要变量，通过白模关闭/开启和加载期/稳定期数据进行对比。

| --- | --- | --- | ---: | --- |
| A | 关闭 | 默认 4x MSAA、原生分辨率 | 148 | 项目基础性能 |
| B | 无裁剪，SSE 16 | 默认 4x MSAA、原生分辨率 | 72 | 白模造成持续显著损失 |
| C | 开启裁剪，SSE 16 | 默认 4x MSAA、原生分辨率 | 72 | 与 B 相同，裁剪无可测额外损失 |
| D | 开启裁剪，SSE 32 | 默认 4x MSAA、原生分辨率 | 72 | 与 C 相同，提高 SSE 无可测改善 |

| G | 开启裁剪，SSE 16 | MSAA 关闭、原生分辨率 | 152 | 原始模型精度下最终验证通过 |


## 4. 根因判断

证据链如下：

1. 不启用裁剪时白模仍从约 148 FPS 降到约 72 FPS，说明裁剪不是主要原因。
2. 开启裁剪后最低和稳定 FPS 均未变化，进一步排除裁剪的显著影响。
3. SSE 从 16 增至 32 后 FPS 未变化，说明当前视角下调整 LOD 阈值没有减少主要渲染负担。
4. 将内部渲染分辨率降至 50% 后，白模开启与关闭均稳定在约 130 FPS，证明瓶颈与像素渲染负载高度相关。
5. 恢复原生分辨率、仅关闭 4x MSAA 后，白模开启 FPS 恢复至 150 以上，直接定位到多重采样成本。

综合判断：建筑白模包含大量轮廓和几何边缘。4x MSAA 会对这些像素执行多重覆盖采样，放大 GPU 渲染成本；关闭 MSAA 后，每像素采样压力显著下降，因此无需牺牲整体渲染分辨率也能恢复帧率。

## 5. 已实施配置

`frontend/src/config/cesium.config.ts`：

```ts
viewer: {
    // ...
    msaaSamples: 1,
},

whiteModel: {
    url: 'https://buildings.reearth.land/tileset.json',
    maximumScreenSpaceError: 16,
},
```

`frontend/src/views/TransitMapView.vue` 保持原有实现，继续直接应用福田区裁剪；本次性能优化不需要修改页面逻辑。

## 6. 后续建议

- 将当前配置作为默认方案，不需要切割离线瓦片或移除福田区裁剪。
- 在不同高度、俯仰角和窗口尺寸下各做一次回归测试，避免结论只覆盖单一视角。
- 在目标部署设备上复测，尤其关注高 DPI 屏幕和集成显卡。
- 如果后续发现建筑边缘锯齿不可接受，可单独测试 `msaaSamples: 2`，不要直接恢复 4x MSAA。
- 将稳定 FPS、加载期最低 FPS 和画质一起作为回归指标；即时 FPS 小幅波动不应单独作为结论。
